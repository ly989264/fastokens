# 前缀缓存对推理请求放开

基线：远端 main `508cbe4`。本 commit 的代码改过两版：第一版在本地评审时编号 `9b80e23`（未推送），在它上面做了完整的 5 个种子的实验；评审后改了替换规则、加了字节预算和缓存清空（第 1 节），再在最终代码上重跑主表等关键实验，确认数字一致（第 3.3 节）。结论只用 `508cbe4` 基线上的数字；更早基线上的数据放在第 7 节，只作参考。机器：M2 Pro（6 性能核 + 4 能效核），macOS；所有计时都在 `perflock` 下运行。

## 1. 做了什么

- **问题**：前缀缓存的开关 `FASTOKENS_INPUT_CACHE=<条数>` 对推理请求从来不起作用。它只处理"整个输入不含任何特殊标记"的情况，而推理请求是 chat template 渲染出来的，里面全是 `<|user|>`、`<|assistant|>`、`<tool_call>` 这类特殊标记。
- **改动**：
  - 同一个开关、同一个容量，现在对含特殊标记的输入也生效。相对"不开缓存"，结果逐 token 一致。不含特殊标记的纯文本仍走原来的逻辑。
  - **内存上限**：推理请求这部分除了条数，还受字节预算限制：`FASTOKENS_INPUT_CACHE_MIB=<MiB>`，默认 2048。条数或字节数任一超限，就淘汰最久没用的条目；单条成本超过预算 1/64 的请求不缓存（和段缓存的规则一样）。
  - **替换规则**：新请求只有在"延续被复用条目的那个会话"时才替换它。只和它共享系统提示的其他会话不再互相顶掉（第 4.7 节）。
  - **缓存清空**：改词表（`add_tokens`）和改 normalizer（`set_normalizer`）都会清空三种缓存（纯文本前缀缓存、推理请求前缀缓存、段缓存）。main 上 `set_normalizer` 什么都不清。
- **观测**：新路径接入 `observe` 特性，指标在 `prefix_cache.chat` 下：完整命中 / 前缀复用 / 未命中；复用与重新编码的字节数、复用的 token 数；切点回退、无可用切点、绕过次数；写入 / 替换 / 淘汰；过大未存、清空；占用字节、字节预算、索引块数；锁竞争。`/metrics`、`top`、dashboard 都能看到，测试逐项对账。
- **测试和工具**：
  - Rust 单元测试和集成测试；
  - 随机差分程序作为默认跳过的测试提交（`tests/prefix_cache_fuzz.rs`）；
  - `examples/agent/` 下：功能对照（`check.py`、`prefix_check.py`）、并发压测（`prefix_soak.py`）、大负载回放基准（`prefix_bench.py`，新增 `--cold`、`--plain`）。
- **不在本次修改范围、只登记**：见第 6 节，包括 main 原有的两个特殊标记切分问题（其中一个是 panic，上游 #78 已修）。

## 2. 怎么做的

### 2.1 实现

含特殊标记的输入交给新的 `PrefixCache`（`src/prefix_cache.rs`），每个请求分四步：

1. **找最像的旧请求**：把输入按 4 KiB 切块，算链式哈希（每块的哈希都包含前面所有块），在索引里找"共享块最多"的缓存条目，再逐字节比对，得到准确的共享长度。成本是扫一遍输入，和缓存了多少条无关。哈希碰撞只会少复用，不会出错。
2. **选切点**：切点是共享部分里特殊标记的起点。选最后一个能用的，规则见第 4.2 节。
3. **只编码剩下的部分**：从切点到结尾走原来的流水线；段缓存开着时，这部分也走段缓存。
4. **存下新请求**：
   - 如果新请求延续了被复用条目的会话，就替换那一条（规则见第 4.7 节）；否则那一条保留，并标为"刚用过"。
   - 条数或字节数超限时，按最近最少使用淘汰。
   - 单条成本超过预算 1/64 的请求不存，它复用的那一条保留。
   - 条目在加锁之前构造好（拷贝输入是最慢的一步），锁内只改索引和 LRU 链表。

`add_tokens` 和 `set_normalizer` 共用一个 `clear_caches()`，清空三种缓存：
- 推理请求前缀缓存以原始输入字节为键，存的 id 依赖词表和 normalizer，规则一变就必须清空。
- 段缓存和纯文本前缀缓存以规范化之后的文本为键，换 normalizer 后旧条目不会再被命中、不会给出错的 id；清空它们只是释放这些再也用不上的条目。

### 2.3 性能实验

- **构建**：
  - 主力是最终代码的 release wheel。4 组只靠环境变量切换：都不开 / 只开段缓存（`FASTOKENS_SEGMENT_CACHE=2048`）/ 只开前缀缓存（`FASTOKENS_INPUT_CACHE=<会话数×2>`，字节预算用默认的 2048 MiB）/ 两个都开。
  - 另外两个独立编译的构建，各用自己的 `CARGO_TARGET_DIR`：`508cbe4` 原版，只用于"编进去但不开"的对比；第一版 `9b80e23`，用于新旧替换规则的对比。
- **负载**（`prefix_bench.py`）：
  - GLM-5.2 的 opencode 会话：每个会话有约 45 KB 共享的系统提示和工具定义；工具结果来自真实代码文件；用户发新消息时模板删掉之前各轮的思考内容（改写历史）；历史长到约 70 万字符时压缩。
  - 256 个会话同时进行，每个会话从生命周期中的随机位置加入。加入前的那个请求先编码一遍（不计时），模拟服务已经运行了一段时间。
  - 之后按固定随机种子随机挑会话、发它的下一个请求，共 4000 个，平均每个 36–39 万字符、约 10 万 token。
  - 只计 `Tokenizer.encode(text).ids` 的时间（Rust 编码 + 转成 Python 列表）。"CPU/请求"是编码期间整个进程（含内部线程池）的 CPU，不含渲染模板。
- **重复和顺序**：每个种子的各组放在同一个 perflock 时段里连续跑，顺序按种子轮换；每次记录机器负载；每个种子下各组输出的 token id 都核对一致。主表 5 个种子在第一版上跑；最终代码 2 个种子，第一版的两组放在同一时段里一起跑。
- **容量对等**：主实验里两种缓存都给到"不受容量限制"的程度，并用缓存自报的数字证明（第 3.6 节）。另做两个"内存相同"的对照：段缓存预算设成前缀缓存自报的字节数；前缀缓存的容量压到自报字节约等于段缓存的用量。
- **冷启动**（`--cold`）：所有会话都从第一个请求开始，不预热，相当于服务刚重启。256 个会话，2 个种子，新旧替换规则同一时段对比。另用 ShareGPT 的真实短对话（`--chat --cold`）跑一组。
- **纯文本**（`--plain`）：同样的请求去掉模型的全部特殊标记，变成 ≥4 KiB 的纯文本，这时推理请求前缀缓存只做查找、帮不上忙。开和不开缓存交替 3 轮。
- **其他**：
  - 纯 Rust 单线程回放（去掉 Python 列表这层）；
  - 保留思考内容的对照组（同一模板，不改写历史）；
  - 每个会话文件内容不同的内存测试；
  - `observe` 构建的开销；
  - 1–8 线程扩展；
  - `simulate.py` 服务模拟（1024 个会话，经 transformers 调用，4 个分词线程，按真实节奏发请求）。

### 3.5 纯文本输入的额外开销

同样的 4000 个请求去掉全部特殊标记后，平均 35 万字符的纯文本。GLM-5.2 不走纯文本缓存的扫描器路径，所以开缓存只多做"算块哈希、查一次索引"，然后照常编码，不存。

| 轮次 | 不开 | 开（`FASTOKENS_INPUT_CACHE=512`） | 耗时 | CPU |
|---|---|---|---|---|
| 1（先不开） | 9.74 s | 9.86 s | +1.2% | +0.2% |
| 2（先开） | 9.75 s | 9.84 s | +0.9% | +0.6% |

## 4. 原理如何

### 4.1 为什么原来不生效

原来的前缀缓存挂在"整个输入是一段纯文本"的扫描器快路径上，切点也只能放在纯文本内部的换行处。推理请求一定含特殊标记，进不了那条路径。另外，原来的缓存命中后不用新请求更新条目，多轮对话里永远只能复用第一次存下的那一版。

### 4.2 切点为什么是安全的

特殊标记在一切处理之前，先在原始文本上匹配出来；之后的规范化、预切词、BPE 都是在两个标记之间各自进行的。所以一个标记之前的所有 token，不受这个标记之后写了什么的影响。前提是新请求在这里也被切成同样的样子。共享的字节保证了这一点，只有两个例外：

1. **一个更长的标记从切点或切点之前开始、越过了共享部分的末尾**。例如共享部分以 `x<|b|>` 结尾，新请求接着是 `y`，而 `x<|b|>y` 本身是一个标记，新请求在这里就会切成不同的样子。匹配是"最左最长"，能这样越界的标记只能从共享部分末尾往前最多"最长标记长度"个字节的位置开始，所以只需在新请求上检查这几十个位置。
2. **有标记从切点标记的 `lstrip` 吞掉的空白里开始**。从切点开始单独编码时，这块空白前面的上下文没了，结果可能不同。

遇到这两种情况就退回到更早的切点。在 main 上，`lstrip` 只会把标记的起点往左挪、并且不越过上一个标记的末尾，所以切点永远不会落在标记文字之后；上游 v0.3.4 不同，那里需要额外处理。代码里仍然取"覆盖范围起点"和"文字起点"中较早的一个作为切点，以防将来合入上游。

### 4.3 为什么前缀缓存在"历史追加"的请求上比段缓存快

两种缓存都只需要真正编码新加进来的内容，差别在"确认哪些部分可以复用"的成本：

- 段缓存要处理整个输入：在全部文字上找特殊标记，把每一段都算哈希、查表、核对内容，再把每一段的 id 复制拼接起来。一个 10 万 token 的请求有上千段，这些工作和输入总长度成正比。
- 前缀缓存对共享部分只做三件事：对整个输入算一遍块哈希，和找到的旧条目逐字节比一遍，把共享部分的 id 整块复制一次。这些都是连续内存上的批量操作，比逐段处理便宜。只有切点之后的少量文字才需要找特殊标记、编码。

纯 Rust 回放里单请求中位数 0.36 ms 对 0.18 ms，就是这部分成本的差别。经 Python 调用时，两者都还要把约 10 万个 id 转成 Python 列表，所以差距缩小到约 16%。

### 4.4 为什么"用户新发言、改写历史"的请求上前缀缓存比段缓存慢

GLM-5.2 的模板只保留"最后一条用户消息之后"各轮回复里的思考内容。用户一发新消息，上一轮所有回复里的思考内容都会被删掉。于是新请求从"上一条用户消息之后的第一个回复"开始，就和上一个请求不一样了：

- 前缀缓存只能复用到第一个不同的字节。改写点之后的整段内容（通常是上一轮的全部工具调用和工具结果，很长）都要重新编码。
- 段缓存按内容查找每一段。改写点之后，被删掉思考内容的回复段确实变了，要重新编码；但工具结果这些段的内容没变，照样命中。

对照实验证明了原因：同一个模板改成保留思考内容（不改写历史）之后，这类请求上前缀缓存反而比段缓存快 22%。

### 4.5 为什么两个都开最快

两个都开时，前缀缓存在前面，段缓存处理切点之后的部分：

- 历史追加的请求：前缀缓存把共享部分整块复用掉，剩下的只是新内容，段缓存在这里也没东西可复用，所以和只开前缀缓存一样快（1.00 vs 1.04 ms）。
- 改写历史的请求：前缀缓存复用到改写点；改写点之后那一大段交给段缓存，没变的段直接命中，所以和只开段缓存一样快、甚至更快（0.95 vs 1.10 ms）。

每类请求都拿到了两种策略里更好的那一个。代价是两份内存：段缓存约 150 MiB 加前缀缓存约 280 MiB（256 会话）。

### 4.6 为什么内存相同时前缀缓存反而慢很多

前缀缓存按条数管理：每个活跃会话需要一条，一条就是这个会话完整的最新请求（文本加 id，约 0.8 MiB）。段缓存按内容去重，会话之间共享的系统提示、工具定义和相同的文件只存一份。

当前缀缓存的条数少于活跃会话数时（190 条对 256 个会话），各会话的请求随机交错到来，一个会话的条目往往在它下一次请求之前就被淘汰。这个请求就只能复用到别的会话共享的系统提示，几乎要整段重新编码。所以前缀缓存的容量应设为活跃会话数的 1.5–2 倍，给"用户新发言后旧版本还没被淘汰"留余量。

### 4.7 替换规则：什么时候新请求替换旧条目

一个会话只需要保留最新的一条，旧的那条应该被替换掉，否则它占着条数和内存，直到被淘汰。难点是：缓存不知道请求属于哪个会话，只能从"共享了多少字节"来判断。

- **第一版的规则**："新请求与旧条目共享至少一半"就替换。会话前期的历史比系统提示短，这条规则就会出错。opencode 的系统提示和工具定义约 45 KB，一个会话的条目小于约 90 KB 时，另一个会话的新请求只共享系统提示也超过一半，于是替换掉它。冷启动时所有会话都处在前期，结果几乎只剩一条条目在被各会话轮流替换：每个请求只能复用系统提示，自己的历史每次都要重新编码。第一版的"复用了 85.4% 字节"里大部分就是系统提示。
- **最终的规则**：每个条目记住"它和别的会话共享的前缀有多长"（下称"公共部分"）：
  - 这个条目是复用别的会话的条目存进来的：公共部分就是当时的共享长度。
  - 它替换了自己会话的旧条目：沿用旧条目的公共部分。
  - 当时什么都没匹配上：公共部分算整条，因为它自己可能就是共享的提示。

  新请求满足下面任一条件才替换：
  1. 包含了旧条目的全部字节：任何以后的请求和它共享的，至少和旧条目一样多，替换没有损失；
  2. 旧条目除公共部分以外的内容，新请求共享了至少一半：这是"同一会话、但历史被改写"的情况，比如删掉思考内容。

  只共享系统提示的其他会话两条都不满足，不再替换；没有替换时，被复用的条目会被标为"刚用过"。
- **代价**：会话前期的一次"用户新发言"往往改写了这个会话大部分的历史，不满足第 2 条，旧版本就留着等淘汰。冷启动 256 会话的实验里因此用满了 512 条、淘汰了 257 条，复用率和速度仍明显更好（第 3.4 节）。热负载下的影响见第 3.3 节。

### 4.8 字节预算和单条上限

- 只按条数封顶时，内存 = 条数 × 单条大小，而单条大小取决于请求有多长。同一个 `FASTOKENS_INPUT_CACHE=512`，10 万 token 的会话约占 280 MiB，长到 100 万 token 就是十倍。所以加了字节预算，条数和字节两个上限同时生效。
- 默认 2048 MiB 的依据：本文测过的配置里最大的是 1024 个会话、每个会话文件不同，自报 1044 MiB，默认值不会让任何一个已测配置因为预算而淘汰。需要更省内存时可以调小，代价按第 4.6 节估算。
- 单条上限是预算的 1/64（默认 32 MiB，约 1400 万字符的请求），和段缓存一样，防止一个巨大的请求把整个缓存挤空。超限的请求照常编码，只是不存；它复用的那一条保留。
- 预算下限 1 MiB：环境变量只接受整数 MiB；Rust 接口传入更小的值时按 1 MiB 算，否则预算小于 64 字节时单条上限变成 0，所有输入都会被默默拒收。
- 预算按每个 `Tokenizer` 实例计：两种缓存都开时，单个实例最多占两者之和（默认 2048 MiB 加段缓存的预算）；vLLM 这类分词器拷贝池里，每份拷贝各占一份。

### 4.9 对推理意味着什么

10 万 token 的请求，GPU prefill 一般要几秒；分词从约 5 ms 降到约 1 ms，对单个请求的首 token 延迟影响很小。收益主要在前端 CPU 和高负载：每个请求的分词 CPU 降到不开缓存的约十分之一，服务模拟里 1024 个会话时，分词带来的延迟 p99 从 132 ms 降到约 20 ms。

## 5. 观测

需要 `observe` 构建（`maturin build --features observe`）。

- `tok.observe()` 的 `prefix_cache`：前缀缓存的总数，纯文本缓存和推理请求缓存的同名字段相加，与原有字段兼容。
- 其中 `prefix_cache.chat` 是推理请求缓存自己的：
  - 查找：`lookups`、`exact_hits`、`prefix_hits`、`misses`；
  - 字节和 token：`lookup_bytes`、`reused_bytes`、`reused_tokens`、`encoded_bytes`（复用 + 重新编码 = 查找）；
  - 切点和绕过：`cut_backoffs`、`no_cut`、`bypass_short`、`bypass_plain`、`marker_fallbacks`（预期为 0）；
  - 写入和移除：`inserts`、`replaced`、`evicted_entries`、`evicted_bytes`、`rejected_oversized`、`rejected_bytes`、`cleared_entries`；
  - 大小：`entries`、`capacity`、`bytes`、`max_bytes`、`index_blocks`；
  - 锁：`lock_contended`、`lock_wait_ns`。

  大小这几项在默认构建里也有。
- 阶段耗时：查找、选切点、写入计入 `prefix_cache` 阶段；新路径的特殊标记切分计入 `added_tokens`，规范化计入 `normalize`。
- `/metrics`：`fastokens_prefix_cache_chat_*`。计数器带 `_total`；`entries`、`bytes`、`max_bytes`、`index_blocks` 是 gauge。`top` 和 `report()` 多一行 "prefix cache (chat)"；dashboard 的缓存卡片多一行"前缀缓存 · 推理请求"。
- 不变式（测试里逐项核对）：
  - `lookups = exact_hits + prefix_hits + misses`；
  - `reused_bytes + encoded_bytes = lookup_bytes`；
  - `entries = inserts − replaced − evicted_entries − cleared_entries`。

## 6. 已知问题和限制

**main 原有问题（只登记，本 commit 不修）：**

- **rstrip + lstrip 的 panic**：一个带 `rstrip` 的特殊标记吞掉的空白里，开始一个"以空白开头、又带 `lstrip`"的特殊标记时，main 的全量扫描切分会因为切片范围倒置而 panic（Python 里是 `PanicException`），开不开缓存都一样。上游 v0.3.4 的 #78 已修（`lstrip` 的起点不早于上一个标记的末尾）。
- **两条切分路径结果不同**：一个 `rstrip` 吞掉的空白恰好是下一个特殊标记文字的开头时，memchr 预筛选路径（起始字节 ≤ 3 种）和全量扫描路径（> 3 种）切出的结果不同。缓存不受影响：开和不开走的是同一条路径，测试也两条路径都覆盖了。
- 本次测过的 16 个真实模型都没有带 `lstrip`/`rstrip` 的特殊标记，这两个问题都不会触发。

**观测计数的语义：**

- `bypass_plain`：不含特殊标记的输入，要先算块哈希、查一次索引，切分时才发现没有标记。这次查找不计入 `prefix_cache.chat.lookups`：
  - 在扫描器路径上（o200k / Kimi 类切词规则），纯文本缓存接着会再查一次并计数，相加后的 `prefix_cache.lookups` 里每个请求只算一次；
  - 在 HF 正则类分词器上（如 GLM-5.2），≥4 KiB 的纯文本输入做了这次查找，但哪边都不计数，只体现在 `bypass_plain` 里。
- 占位 id 冲突回退（`marker_fallbacks`，只在模型 id 恰好等于 `u32::MAX − 1` 时发生）会调用两次 `begin_encode`，前一次的阶段计时被丢掉。实际模型不会出现。
- 已修：第一版里 `clear()` 不计数，`add_tokens` 之后 `entries = inserts − replaced − evicted` 就不成立了；现在加了 `cleared_entries`。

**缓存本身：**

- **索引按块哈希"最新者胜"**：多个条目有同一个块时，索引只记最新写入的那个。最新的那个被替换或淘汰后，这些块从索引里删掉，更早的条目在这些块上就找不到了；还能靠更深、只属于自己的块被找到，但那些只和它共享前面几块的输入找不到它。代价只是少复用，不影响正确性。
- **改写后不替换的旧版本占着槽位**：会话前期一次"用户新发言"改写了大部分历史时，新请求不替换旧版本（第 4.7 节）。旧版本改写点之后的块再也不会出现在这个会话的请求里，之前的块在索引里又被新版本接管，所以它实际上已经找不到了，只是占着一个槽位和它的字节，等 LRU 淘汰。
  - 现有数据（冷启动实验，256 会话 × 4000 请求，容量 512）：写入 3976、替换 3207，即 769 条没有替换旧条目（其中 256 条是各会话的第一个请求）。结束时 512 条全满，淘汰了 257 条。
  - 热负载下影响小：结束时 375 条，比第一版多 32 条，淘汰 0。
  - 所以容量建议取活跃会话数的 1.5–2 倍。改进思路：替换时也检查同一会话的更早版本，或在索引失去最后一个块时直接回收这一条。
- **改写历史的请求**：前缀缓存只能复用到改写点，这类请求上比段缓存慢（第 4.4 节）。和段缓存一起开就没有这个问题。
- **短输入**：短于 4 KiB 的输入不查找。ShareGPT 这类短对话里接近一半的请求属于这种，只有段缓存能帮上（第 3.4 节）。
- 纯文本部分（扫描器路径上的原有缓存）仍只按条数限制。
- 只在 macOS M2 Pro 上测过。

**可能的改进（这次不做）：**
- 让调用方传一个会话标识（例如 vLLM / SGLang 的请求里通常有），替换和淘汰就不必猜。
- 索引对同一个块记多个条目，或在淘汰时把块重新指回仍然存在的条目，可以去掉"最新者胜"的损失。
- 对纯文本可以先确认有没有特殊标记再查找，省掉约 1% 的开销。

## 7. 参考数据（不作结论）

- **fork main `2081eb9`（变基前）**：同样的负载，5 个种子：段缓存 4.26–4.34 倍、前缀缓存 4.72–4.79 倍、两个都开 5.24–5.39 倍。当时段缓存组用的是 `2081eb9` 原版构建、另两组用新构建，多了一个变量；结论与本次一致。
- **上游 v0.3.4（本地移植，未提交）**：v0.3.4 不开缓存时本身就比 `508cbe4` 快约 4.2 倍（同样负载 4.97 s 对 20.97 s，主要来自上游 #74/#75），所以缓存带来的倍数小得多：前缀缓存比不开快 1.84 倍。v0.3.4 的 `single_word` 和两阶段 `normalized` 匹配需要额外的切点规则，`508cbe4` 上没有这两项。
